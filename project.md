# Gravit ERP — суть проекта

> Внутренняя ERP производства металлических входных дверей «Gravit».
> Этот файл — вход в проект: что это, как устроено, какие правила зашиты и почему.
> Технические подробности по экранам и тестам — в `README.md`, сервер — в `docs/server.md`,
> незакрытые планы — в `finance-plan.md` и `roles-and-settings-plan.md`.
>
> Состояние на 19 сентября 2026: 410 тестов, проходят на SQLite и на MySQL.

---

## 1. Что это

Одно приложение для продаж, завода, финансов, кадров и клиента:

| Кто | Где работает | Что делает |
|---|---|---|
| **Отдел продаж** | `/admin` | ведёт сделки по воронке: заявка → замер → договор → передача на завод → отгрузка → закрытие |
| **Завод** | `/admin` (начальник производства) и планшет `/shop` (рабочие, вход по коду) | выполняет наряды по 13 этапам цеха, получает сдельную оплату за каждый закрытый этап |
| **Финансы** | `/admin`, группа «Финансы» | счета, поступления, расходы, касса и банк, долги, зарплата, бонусы |
| **Кадры** | `/admin` | сотрудники, ведомости, бонусы |
| **Директор** | `/admin` | всё, плюс настройки: роли и доступы, воронки, прайс, экран цеха, финансы |
| **Клиент** | `/track/{hash}` по QR | смотрит статус своего заказа без входа в систему |

Ключевая идея — **две связанные воронки**. Сделка продаж, дойдя до этапа «Передано в производство», сама создаёт наряд в воронке завода и списывает материалы со склада. Когда завод закрывает этап с флагом «завершает производство» («ОТК и упаковка»), сделка продаж сама становится «Готово к отгрузке». Пока наряд в цеху, менеджер сделку двигать не может — её ведёт завод.

Вторая идея — **всё, что можно, настраивается из панели, а не в коде**: этапы воронок и их обязательные поля, прайс, права ролей, процент бонуса. Это сделано, чтобы владелец менял систему сам.

## 2. Стек и запуск

- PHP 8.5, Laravel 12, Filament v4 (панель), Livewire 3, Tailwind 4. Внешних библиотек для графиков и календарей нет: QR и диаграммы — inline-SVG/CSS.
- База: SQLite для разработки (`database/database.sqlite`), **MySQL 8+ в бою** (hoster.kz). SQL в коде не привязан к движку; весь набор тестов проходит на обоих: `php artisan test` (SQLite в памяти) и `composer test:mysql` (локальный MySQL, база `gravit_test`).
- Файлы (договоры, чеки, аватары) — **закрытый диск** `storage/app/private`: наружу отдаются только по подписанной ссылке на 30 минут (`app/Support/Uploads/PrivateFiles.php`), без входа файл не открыть. Диск задан один раз для всех полей загрузки в `AppServiceProvider`.
- Проверка кода: PHPUnit (410 тестов), Larastan уровень 5 (50 известных ошибок про `$this->record` в страницах Filament — это базовый долг, не увеличивать), Pint.
- Сборка фронтенда `public/build` **хранится в git**: на боевом сервере с 1 ГБ памяти Node не ставится.

Запуск локально: `composer install && npm install && npm run build && php artisan migrate --seed && php artisan serve --port=8080`.

Демо-доступы после `--seed` (пароль `password`): `admin@gravit.kz` (директор), `manager@`, `accountant@`, `hr@`, `surveyor@`, `master@` (начальник производства), `worker@`. Код планшета цеха — **Настройки → Экран цеха**.

Код — в приватном репозитории `github.com/baproger/gravitdoors.kz`, ветка `main`. **Бой — виртуальный хостинг hoster.kz с Plesk** (тариф «Турбо-1»: 15 ГБ, 1 ГБ, 2 vCPU, PHP 8.3/8.4, без root): Plesk → Git тянет `main` по deploy-ключу в каталог `gravit`, веб-корень `gravit/public`, действие при развёртывании `bash deploy/plesk-deploy.sh`, планировщик раз в минуту `artisan schedule:run`, первый запуск `php artisan gravit:install`. Пошагово — `docs/plesk.md`. Зависимости закреплены под PHP 8.3+ (`config.platform.php`), на сервере выбирается 8.4. Инструкция для VPS (`docs/server.md`, `deploy/bootstrap.sh`) — на случай переезда.

**Важно про базу.** `migrate:fresh` стирает всё, включая настроенные руками этапы и права. Один раз это уже случилось: 13 этапов цеха пришлось восстанавливать. Поэтому боевая цепочка цеха теперь в сидере `GravitFactoryStagesSeeder` и накатывается последней при любом `--seed`. На боевом сервере `migrate:fresh` не запускать; для проверок есть тесты в памяти и `gravit:backup`.

## 3. Модель данных

```
users ─┬─ deals (сделка продаж) ─────┬── deals (наряд завода, parent_deal_id)
       │      │                       │      └── production_logs (этап цеха: кто, когда, сдельная оплата)
       │      ├── door_configurations (двери заказа)
       │      ├── deal_payments (платежи с чеками) ──→ cash_movements
       │      ├── deal_events (история: кто, из какого отдела, что сделал)
       │      ├── deal_stage_visits (журнал заходов на этапы)
       │      └── bonuses (автобонус менеджеру, deal_id)
       │
       ├─ factory_stages (этапы ОБЕИХ воронок: pipeline_type = sales | factory)
       ├─ door_options (прайс конфигуратора по группам)
       ├─ material_stocks + stock_movements (склад и движения, в т. ч. факт по наряду)
       │
       ├─ expenses (расходы: категория, статус, чек) ──→ cash_movements
       ├─ cash_accounts + cash_movements (касса и банк: журнал, остаток считается)
       ├─ debts + debt_payments (долги компании; платёж = расход + движение)
       ├─ salary_sheets + salary_payments (ведомость за месяц; выплата = расход + движение)
       ├─ bonuses (бонусы сотрудникам, ручные и автоматические)
       │
       ├─ role_permissions (отличия матрицы прав от рекомендованной)
       └─ settings (код планшета, процент бонуса, автоутверждение)
```

**Сделка и наряд — одна таблица `deals`.** Наряд — это отдельная строка с `pipeline_type = factory` и ссылкой `parent_deal_id` на сделку продаж. В наряд копируются сумма, себестоимость, клиент, телефон, адрес, менеджер и срок; своих дверей у наряда нет, он берёт позиции у сделки. Цех этих сумм не видит только потому, что право «Суммы в карточках» у него на «Нет» — данные в строке есть.

**Этапы обеих воронок — одна таблица `factory_stages`.** Колонка `pipeline_type` разделяет воронки. Флаги автоматизации (`triggers_production` у продаж, `completes_production` у завода), норматив часов, сдельная расценка, обязательные поля — в этапе, настраиваются в админке.

**Позиция прайса записана в дверях парой «группа + код».** Поэтому код и группу нельзя менять после создания, а позицию из заказа нельзя удалить — только снять с продажи.

**Деньги — одна цепочка.** Платёж по сделке и подтверждённый расход порождают движение по счёту (`CashLedger`); платёж по долгу и выплата зарплаты порождают расход, а он — движение. Остаток счёта не хранится, а считается по журналу. Так нельзя рассинхронизировать кассу правкой поля.

Статусы, роли, категории, права — PHP-enum'ы в `app/Enums` (`DealStatus`, `UserRole`, `Permission`, `AccessLevel`, `ExpenseCategory`, `StageRequirement`, `Department` и др.).

## 4. Роли и доступы

Семь ролей: **Директор** (`admin`), **Менеджер продаж**, **Бухгалтер-финансист**, **HR-директор**, **Начальник производства** (`master`), **Рабочий цеха**, **Замерщик**. Роль назначается в карточке сотрудника.

Что роль видит и может — не в коде, а в матрице **Настройки → Роли и доступы** (`/admin/access`, только директор). У каждой роли уровень по каждому из 32 прав:

| Уровень | Что значит |
|---|---|
| **Нет** | пункт меню скрыт, прямая ссылка → 403 |
| **Чтение** | видно, но без создания, правки, перетаскивания и действий; карточка сделки открывается отдельной страницей просмотра |
| **Только свои** | видно и можно менять лишь записи, где сотрудник — ответственный; чужая сделка отдаёт 404 |
| **Полный** | без ограничений |

Рекомендованная матрица (`—` нет · `Ч` чтение · `С` только свои · `П` полный) — она же значения по умолчанию, в базе хранятся только отличия:

| Раздел | Менеджер | Директор | Бухгалтер | HR | Производство | Рабочий | Замерщик |
|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| Воронка продаж | С | П | Ч | — | — | — | — |
| Воронка завода | Ч | П | Ч | Ч | П | Ч | — |
| Просроченные | С | П | Ч | Ч | П | — | — |
| Сделки и наряды | С | П | П | — | Ч | Ч | — |
| Склад и движения | Ч | П | П | — | П | — | — |
| Моя зарплата | П | П | П | П | П | П | П |
| Финансы: обзор, счета, поступления, расходы, касса, долги | — | П | П | — | — | — | — |
| Зарплата цеха, ведомость, бонусы | — | П | П | П | — | — | — |
| Настройки: сотрудники | — | П | Ч | П | — | — | — |
| Настройки: экран цеха | — | П | — | — | П | — | — |
| Настройки: воронки, прайс, справочники, роли | — | П | — | — | — | — | — |

Отдельные полномочия внутри экранов: удаление сделок (только директор), отказ от сделки (менеджер — своей), блокировка отгрузки (финансы), сводные суммы воронки (директор, бухгалтер), суммы на карточках, **подтверждение расходов, бонусов и выплат** (отдельное право: сняв его, директор оставляет проверку за собой, а раздел остаётся рабочим), оклады и ставки (финансы, кадры), факт материалов (цех).

Как устроено: `Permission` и `AccessLevel` — перечни, `App\Services\AccessControl` — реестр (кэш + память запроса + отличия в `role_permissions`), политики в `app/Policies` спрашивают уровень у него. Прямых сравнений с ролью в коде нет. Инфопанель, списки, канбаны, поиск и прямые ссылки фильтруются одним scope `Deal::visibleTo()`.

**Директор всегда имеет полный доступ** (`Gate::before`), его строку в матрице изменить нельзя — иначе систему можно запереть без хозяина. Поэтому запреты «нельзя удалить подтверждённое / занятое / с нарядом в цеху» живут в моделях (`canBeDeleted()`) и в действиях, а не только в политиках.

Приёмка по ролям автоматизирована: `RoleMatrixAcceptanceTest` обходит все разделы под каждой ролью.

**Защита снаружи.** Вход: 5 попыток в минуту, второй фактор через приложение-аутентификатор (профиль → «Двухфакторная аутентификация», коды восстановления). Файлы — закрытый диск и подписанные ссылки. Заголовки безопасности и HSTS на каждом ответе, куки только по HTTPS. Публичные адреса `/track` и `/shop` под лимитом запросов и кодом. Все действия проверяются политиками на сервере; сумму сделки, статус и этап руками не поменять. Проверка: `tests/Feature/SecurityHardeningTest.php`.

## 5. Как течёт сделка

1. **Заявка.** Менеджер заводит сделку: клиент (физлицо/компания, БИН, телефоны, адрес, источник), двери (линейка, модель, размеры, металл, МДФ, замок, утеплитель, покрытие, опции), срок сдачи (обязателен). Цена считается сама из прайса: `габариты × цена за м²` + фиксированные опции + сборка + доставка + монтаж; руками сумму не поменять.
2. **Замер.** Дата замера → уведомление замерщику и начальнику производства (без ссылки на карточку: им она не открывается). Дата прошла, а сделка не дошла до договора — «замер просрочен», красным.
3. **Договор.** Номер, дата, файл договора. Платежи — каждый с чеком; сумма платежей = предоплата, и она не больше суммы сделки (проверяется на сервере).
4. **Передача на завод.** Вход на этап с `triggers_production`: создаётся наряд, списываются материалы по расходу каждой опции, пишется история. Сделка заблокирована до конца производства. Готовый наряд тоже считается «передано»: второй раз на завод сделка не уходит.
5. **Цех — 13 этапов.** Согласование дизайна → создание чертежа → раскрой материала → лазерная резка → гибка листа → сварка и сборка → полимерная покраска → МДФ и стекло → фурнитура и замки → сборка заказа → **ОТК и упаковка** (завершает наряд) → доставка → монтаж. Рабочий на планшете нажимает «Взял» / «Готово» (без выбранного исполнителя «Готово» не срабатывает); начальник производства двигает наряды на канбане и отмечает факт материалов сверх плана. Сдельная оплата за этап — тому, кто взял его в работу, иначе тому, кто закрыл, если это цех; директор, закрывший этап с канбана, оплату не получает. Расценка фиксируется в момент закрытия.
6. **Готово к отгрузке.** Завод закрыл этап с `completes_production` → сделка продаж сама переходит дальше со статусом «Готово к отгрузке». Финансы могут поставить **блокировку отгрузки** с причиной: цех работает, но дальше передачи в цех сделка не пойдёт, пока долг не закрыт.
7. **Доставка и монтаж → Сделка закрыта.** Закрыть можно только при полной оплате. Завершающий этап ставит «Завершена» и начисляет **автобонус менеджеру** — процент от суммы сделки (по умолчанию 2 %, ставка в «Настройки → Финансы», у сотрудника может быть своя), один раз на сделку, в месяц закрытия, на утверждение или сразу — по настройке.

Отмена наряда: материалы возвращаются на склад по сальдо «списано − возвращено», сделка возвращается на шаг назад и её можно передать заново. Отмена сделки: кнопкой в шапке карточки, живой наряд отменяется вместе с ней.

Открытый вопрос владельцу: этапы «Доставка» и «Монтаж» стоят в воронке завода **после** «ОТК и упаковка», но наряд закрывается на ОТК, и до них не доходит. Либо перенести флаг завершения на «Монтаж» (одним кликом в «Этапы воронок»), либо убрать эти два этапа из цеха — доставку и монтаж тогда ведут продажи своим этапом.

## 6. Правила, которые нельзя обойти (все проверяются на сервере)

**Воронка**
- Вперёд — только на соседний этап; назад — свободно.
- Вход на этап требует обязательных полей (настраиваются в «Этапах воронок»).
- Пока наряд в цеху, сделку продаж не сдвинуть ни вперёд, ни назад.
- Блокировка отгрузки не пускает сделку дальше этапа передачи в цех; ставится и снимается только с правом «Отметка оплаты», с обязательной причиной, пишется в историю.
- Статус сделки следует за этапом и в карточке только для чтения; отмена — отдельной кнопкой.
- Поле «Этап» в карточке — только для чтения; этап меняется полосой этапов или на канбане.
- Автоматика в воронке — ровно один этап; выключить нельзя, только передать другому. Такой этап не удаляется и не скрывается.
- Этап со сделками удаляется только с переносом сделок (не на завершающий); этап цеха с работами — не удаляется (по нему считается зарплата).
- Сделку с нарядом в цеху не удалить; живой наряд не удаляется, а отменяется; материал с движениями или позициями прайса не удаляется. Сделка без ответственного видна всем на уровне «только свои», чтобы не потеряться.

**Прайс**
- Снять с продажи ≠ удалить: снятая позиция не предлагается новым дверям, но в старых заказах считается и списывается.
- Позицию, выбранную хоть в одной двери, удалить нельзя. Вариант по умолчанию в группе один.

**Деньги**
- Платёж без чека не сохраняется; сумма платежей не больше суммы сделки. Все загрузки (чеки, договоры, аватары) сжимаются при сохранении: фото до 1600 px / JPEG 82 %, PDF через Ghostscript, если он есть (`app/Support/Uploads/UploadCompressor.php`, подключён ко всем полям загрузки в `AppServiceProvider`). Если спецификацию урезали ниже внесённого, карточка предупреждает.
- Расход попадает в сводку и списывается со счёта только после подтверждения; для всех категорий, кроме зарплаты и налогов, нужен чек. Подтверждённый расход не удаляется — только отклоняется с причиной.
- Ведомость: удержания правятся только в черновике; утверждённая зафиксирована (повышение оклада не меняет прошлый месяц); выплата не больше остатка и только по утверждённой; оклад пропорционален дням, если принят внутри месяца.
- Долг: платёж не больше остатка, с остатком не закрывается, с платежами не удаляется.
- Остаток кассы и банка считается по журналу; руками — только перевод между счетами и корректировка с причиной.
- Бонус утверждённый не удаляется, только снимается с утверждения; автобонус — один на сделку.
- Списание материалов при повторной передаче не задваивается; наряд по сделке один.
- Закрытый наряд не берётся в работу, не закрывается и не отменяется повторно.

**Время**
- Время на этапе копится за все заходы (`deal_stage_visits`); норматив сравнивается с суммой.
- Просрочка — только у открытых. Ежедневная проверка и «Просроченные» считают её одинаково. По сроку сдачи продажам показываются сделки, а не их наряды.

## 7. Экраны

**Инфопанель** `/admin` — период (сегодня, неделя, месяц, прошлый месяц, квартал, год, всё время, свой отрезок; живёт в адресной строке) и по нему: продажи (новые, средний чек, портфель, просрочка, конверсия), деньги (поступления с трендом, дебиторка, прибыль, расходы по статьям, касса и банк, долги, столбики по месяцам), цех (наряды, закрытые этапы, средний цикл, застрявшие, загрузка по этапам, выработка), склад (что закупать), люди (к выплате, бонусы на утверждении). Блок появляется только у того, кому открыт раздел.

**Продажи:** Воронка продаж (канбан; итог по колонке — только с правом «Сводные суммы») · Сделки и наряды (вкладки «Отдел продаж» / «Завод» — только открытые, «Все, включая закрытые»; поиск по номеру, клиенту, телефону, БИН; фильтры по воронке, статусу, этапу, менеджеру, источнику, сроку сдачи и дате создания) · Карточка сделки (полоса этапов, вкладки Клиент / Двери / Оплата / Договор, история; для читателей — отдельная страница просмотра; кнопки в шапке по отделам — Отдел продаж / Финансы / Завод / Клиент, «Принять оплату» отдельно с подставленным остатком, та же кнопка на вкладке «Оплата» и в подсказке полосы этапов, когда не хватает только оплаты; все действия — `app/Filament/Actions/DealActions.php`, они же в списке сделок и в «Счетах») · Просроченные (срок сдачи, замер, застряли на этапе).

**Завод:** Воронка завода (на последнем этапе кнопка «Готово ✓») · Планшет цеха `/shop` (крупные карточки, выбор исполнителя, «Взял» / «Готово», без сумм) · Зарплата цеха (сдельно по этапам за месяц).

**Склад:** остатки с минимумом, приход, движения (приход, расход, возврат по наряду, факт сверх плана); фильтры по материалу, периоду, «только по нарядам».

**Финансы:** Обзор `/admin/finance` (ДДС: счета и долги, сумма договоров, дебиторка, поступления, расходы по категориям, результат, склад) · Счета (по сделкам: выставлено, оплачено, остаток; вкладки ожидают / просрочены / оплачены; приём оплаты, напоминание) · Поступления (все платежи, итоги касса/банк) · Расходы (категории, чек, на проверке / оплачено / отклонено) · Касса и банк (счета, журнал, переводы, корректировки) · Задолженности (кому должны, оплата долга) · Зарплата (ведомость: оклад + сдельно + бонусы − удержания; сформировать, утвердить, выплатить) · Бонусы · Моя зарплата (у каждого только своё).

**Настройки (директор):** Роли и доступы · Этапы воронок (конструктор: перетаскивание, цвет, норматив, расценка, обязательные поля, автоматика) · Прайс конфигуратора · Сотрудники (карточка с показателями, оклад и бонусный % — по праву «Оклады и ставки») · Экран цеха (код планшета) · Финансы (процент бонуса, автоутверждение).

**Профиль** `/admin/profile`: своё имя, контакты, фото, пароль. **Клиент** `/track/{hash}`: статус, позиции, сумма, QR.

Везде: календарь с выбором месяца списком и года отдельным полем; фильтры «за период» и «за месяц» на каждой таблице; компактный «Переключить столбцы».

**По расписанию:** 03:00 `gravit:backup` (снимок базы — 14 копий, архив файлов — 3; архив пропускается, если диску останется меньше 1,5 ГБ), 08:00 `gravit:server-check` (диск, память, свежесть бэкапа — директору), 08:30 `gravit:daily-check` (материалы ниже минимума, наряды дольше норматива — тем, кому открыт раздел).

## 8. Дизайн

Light SaaS / glassmorphism, компактная плотность. Три уровня поверхностей: карточка страницы → плоский серый блок → белый блок внутри. Просрочка и блокировка — красным везде. Токены — в `resources/css/filament/admin/theme.css`, общие правила Filament (модалки, календарь, действия) — в `AppServiceProvider`. Подтверждения — модалки Filament, на планшете — своя. Адаптив проверен на 390 / 820 / 1680 px. Тёмная тема есть, глазами проверена не везде.

17. **Сервер 1 ГБ / 2 vCPU / 15 ГБ** — права, настройки и ворота замера запоминаются на запрос (579 → 4 запроса на матрице прав), сводки считают каждую сумму один раз, график по месяцам 24 → 2 запроса, логи 7 дней, бэкап с ротацией, сборка в git, `deploy.sh`, инструкция по PHP-FPM/nginx/cron.
18. **MySQL** — убраны два SQLite-специфичных места (`strftime`, `VACUUM INTO`), бэкап через `mysqldump`, `composer test:mysql`, боевой `.env` под hoster.kz.
19. **Чтобы сервер не задыхался** — замер всех страниц (≤ 53 запроса, ≤ 100 мс), опрос уведомлений раз в 2 минуты вместо 30 секунд, бэкап файлов 3 копии вместо 14 с защитой от переполнения диска, `gravit:server-check` (диск, память, бэкап) с уведомлением директору, планировщик без наложений, swap и лимиты nginx на публичные адреса в `docs/server.md`, проверка диска в `deploy.sh`; `deploy/` с готовыми конфигами и скриптами настройки сервера и заливки по rsync, `gravit:install` для первого запуска без демо-данных; бой оказался виртуальным хостингом с Plesk — `docs/plesk.md`, `deploy/plesk-deploy.sh`, `deploy/build-release.sh`, зависимости закреплены под PHP 8.3+. Попутно: бэкап определял движок по имени соединения, а не по драйверу; откат миграций падал на SQLite (индекс `bonuses.source`) и на MySQL (индексы `deals`, которые перехватили внешние ключи) — теперь `migrate:reset` проходит на обоих.
20. **Оплата и кнопки в карточке по отделам** — владелец не находил, как закрыть оплату, чтобы завершить сделку: платёж жил в репитере вкладки «Оплата» и требовал «Сохранить». Теперь все действия по сделке в `DealActions`: «Принять оплату» с подставленным остатком (первый платёж — вся сумма договора) в шапке карточки, на вкладке «Оплата» и прямо в подсказке полосы этапов; остальные кнопки сгруппированы по отделам (Отдел продаж / Финансы / Завод / Клиент), те же действия в списке сделок и в «Счетах». Бухгалтер и мастер работают со страницы просмотра — кнопки есть и там.
21. **Сжатие загрузок** — диск 15 ГБ, а фото чека с телефона 4–8 МБ. `UploadCompressor` подключён ко всем полям загрузки одной настройкой: фото до 1600 px и JPEG 82 % (с прозрачностью — WebP), разворот по EXIF, PDF через Ghostscript при его наличии, Word без изменений; уменьшение начинается ещё в браузере. `ext-gd` и `ext-exif` объявлены в composer.
22. **Безопасность перед боем** — файлы переведены на закрытый диск с подписанными ссылками (раньше чек открывался по прямому адресу без входа, а поле без ограничения типов позволило бы положить исполняемый файл в веб-корень); заголовки безопасности на каждый ответ (`SecurityHeaders`: X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy, HSTS по https); HTTPS принудительно, куки сессии только по https, доверенные прокси; двухфакторный вход через приложение-аутентификатор с кодами восстановления (секрет и коды зашифрованы в базе), включается в профиле. `composer audit` и `npm audit` — без известных уязвимостей.

## 11. Что осознанно не сделано / на будущее

**Открытые вопросы владельцу**
- Куда ставить флаг «завершает производство» — на «ОТК и упаковка» (сейчас) или на «Монтаж», если доставку и монтаж делает цех (см. §5).
- Новые роли из интерфейса (например, «Кладовщик») пока нельзя создать: роли — перечень в коде. Нужен справочник ролей с копированием прав — отдельный шаг плана.
- Нормативы часов и расценки у семи восстановленных этапов цеха стоят по нулям — проставить в «Этапах воронок».

**Часть B плана ролей и настроек** (`roles-and-settings-plan.md`, шаги 10–16, не начата): реквизиты компании и логотип, коэффициенты расчёта из `config/gravit.php` в настройки, справочники вместо перечислений (источники, категории расходов, способы оплаты, причины отказа), тексты и подписи, регламенты уведомлений, журнал изменений настроек.

**Финансы** (`finance-plan.md`, шаги 9–12, не начаты): закуп материалов как расход, «Мои расходы» под отчёт, отчёты с экспортом, закрытие периода.

**Известные ограничения**
- Закрытие сделки необратимо из интерфейса.
- Категория и модель двери не влияют на цену — она считается от материалов.
- Переделка готового заказа (второй наряд) не предусмотрена — нужен отдельный «Наряд на переделку».
- Статусы «Отгружено» и «Установлено» есть в перечне, но не ставятся.
- Склад может уходить в минус (`gravit.allow_negative_stock = true`) — выключить перед боем.
- События `DealHandedToProduction`, `DealStageChanged`, `ProductionCompleted` без слушателей — точки для WhatsApp/1С.
- Колонка `deals.payment_method` не используется; иконка этапа не редактируется в конструкторе; демо-чеки в сидере — `.txt`.
- Не сделаны: печатные формы (наряд с QR, счёт, договор), ТВ-экран с рейтингами, CI.
