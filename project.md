# Gravit ERP — суть проекта

> Внутренняя ERP производства металлических входных дверей «Gravit».
> Этот файл — вход в проект: что это, как устроено, какие правила зашиты и почему.
> Технические подробности по экранам и тестам — в `README.md`.

---

## 1. Что это

Одно приложение для двух отделов и клиента:

| Кто | Где работает | Что делает |
|---|---|---|
| **Отдел продаж** | `/admin` | ведёт сделки по воронке: заявка → замер → договор → передача на завод → отгрузка → закрытие |
| **Завод** | `/admin` (мастер) и планшет `/shop` (рабочие, вход по коду) | выполняет наряды по этапам цеха, получает сдельную оплату за каждый закрытый этап |
| **Клиент** | `/track/{hash}` по QR | смотрит статус своего заказа без входа в систему |

Ключевая идея — **две связанные воронки**. Сделка продаж, дойдя до этапа «Передано в производство», сама создаёт наряд в воронке завода и списывает материалы со склада. Когда завод закрывает последний этап («ОТК и Упаковка»), сделка продаж сама становится «Готово к отгрузке». Пока наряд в цеху, менеджер сделку двигать не может — её ведёт завод.

---

## 2. Стек

- PHP 8.5, Laravel 12, Filament v4 (админ-панель), Livewire 3, Tailwind 4.
- База — SQLite для разработки (`database/database.sqlite`); сессии и очередь — в базе.
- Файлы (договоры, чеки, аватары) — публичный диск `storage/app/public` → `public/storage`.
- Проверка кода: PHPUnit (313 тестов), Larastan уровень 5, Pint.

Запуск: `composer install && npm install && npm run build && php artisan migrate --seed && php artisan serve --port=8080`.

Демо-доступы после `--seed`: `admin@gravit.kz`, `manager@gravit.kz`, `surveyor@gravit.kz`, `master@gravit.kz`, `worker@gravit.kz` — пароль `password`. Код планшета цеха: **Настройки → Экран цеха** (меняется при каждом пересеве).

## 3. Модель данных

```
users ─┬─ deals (сделка продаж) ──┬── deals (наряд завода, parent_deal_id)
       │      │                    │       └── production_logs (этап цеха: кто, когда, сдельная оплата)
       │      ├── door_configurations (позиции: двери заказа)
       │      ├── deal_payments (платежи с чеками)
       │      ├── deal_events (история: кто, из какого отдела, что сделал)
       │      └── deal_stage_visits (журнал заходов на этапы)
       │
       ├─ factory_stages (этапы ОБЕИХ воронок: pipeline_type = sales | factory)
       ├─ door_options (прайс конфигуратора по группам)
       ├─ material_stocks + stock_movements (склад и движения)
       └─ settings (код планшета цеха)
```

**Сделка и наряд — одна таблица `deals`.** Наряд — это та же запись с `pipeline_type = factory` и ссылкой `parent_deal_id` на сделку продаж. Так связь «продажи ⇄ завод» остаётся одним JOIN, а не синхронизацией двух сущностей.

**Этапы обеих воронок — одна таблица `factory_stages`.** Колонка `pipeline_type` разделяет воронки. Флаги автоматизации (`triggers_production`, `completes_production`) и обязательные поля (`required_fields`) — в этапе, настраиваются в админке, не в коде.

**Позиция прайса записана в дверях парой «группа + код».** Поэтому код и группу нельзя менять после создания, а позицию из заказа нельзя удалить — только снять с продажи.

Статусы, роли, категории — PHP-enum'ы в `app/Enums` (например `DealStatus`, `UserRole`, `StageRequirement`, `Department`).

## 4. Роли

| Роль | Видит | Не видит |
|---|---|---|
| **admin** | всё, единственный правит этапы воронок, прайс, сотрудников, оклады | — |
| **manager** | сделки, канбан продаж, прайс (без правок), список сотрудников (без окладов), склад | канбан завода; этапы цеха не закрывает (это сдельная оплата) |
| **surveyor** (замерщик) | свою карточку, уведомления о замерах (номер, клиент, адрес, телефон — без ссылки на карточку) | сделки, наряды, склад, просроченные |
| **master** (мастер цеха) | наряды, канбан завода, склад с приходом, своя карточка и зарплата | сделки продаж, деньги сделок |
| **worker** (рабочий) | наряды (список и канбан завода — только просмотр), планшет цеха, своя карточка | всё остальное; кнопок движения на канбане у него нет |

Правила — в `app/Policies`. Администратор проходит любую проверку через `Gate::before`.

## 5. Как течёт сделка

1. **Заявка.** Менеджер заводит сделку: полная карточка клиента (физлицо/компания, БИН, телефоны, адрес, источник), двери (линейка Comfort/Premium/Lux, модель, размеры, металл, МДФ, замок, утеплитель, покрытие, доп. опции), срок сдачи (обязателен). Цена считается сама из прайса: `габариты × цена за м²` + фиксированные опции + сборка + доставка + монтаж.
2. **Замер.** Дата замера → уведомление замерщику. Дата прошла, а сделка не дошла до договора — «замер просрочен», красным.
3. **Договор.** Номер, дата, загрузка подписанного договора. Платежи — каждый с обязательным чеком; сумма платежей = предоплата.
4. **Передача на завод.** Вход на этап с `triggers_production`: создаётся наряд, списываются материалы по расходу каждой опции (агрегировано по материалу), пишется история. Сделка заблокирована до конца производства.
5. **Цех.** Наряд идёт по этапам подряд: раскрой → сварка → покраска → утепление и МДФ → фурнитура → ОТК и упаковка. Рабочий на планшете нажимает «Взять в работу» / «Готово» (без выбранного исполнителя «Готово» не срабатывает). Сдельная оплата за этап — **тому, кто взял его в работу**, а без «Взять в работу» — тому, кто закрыл, если это мастер или рабочий. Администратор, закрывший этап с канбана, оплату не получает: этап остаётся без исполнителя и без начисления. Расценка фиксируется в момент закрытия.
6. **Готово к отгрузке.** Завод закрыл этап с `completes_production` → сделка продаж сама переходит дальше со статусом «Готово к отгрузке».
7. **Доставка и монтаж → Сделка закрыта.** Закрыть можно только при полной оплате. Завершающий этап ставит статус «Завершена»; закрытая сделка не двигается.

Отмена наряда: материалы возвращаются на склад по сальдо «списано − возвращено» (повторная отмена ничего не задваивает), сделка возвращается на шаг назад и её можно передать заново.

## 6. Правила, которые нельзя обойти (все проверяются на сервере)

**Воронка**
- Вперёд — только на соседний этап; назад — свободно.
- Вход на этап требует обязательных полей (настраиваются в «Этапах воронок»): телефон/адрес для замера; замер, двери, срок для договора; договор, документ, предоплата для передачи на завод; полная оплата для закрытия.
- Пока наряд в цеху, сделку продаж не сдвинуть ни вперёд, ни назад.
- Статус сделки следует за этапом (до передачи — «В работе», после завода — «Готово к отгрузке», завершающий этап — «Завершена»); в карточке он только для чтения. Отмена — кнопкой «Отменить сделку» в шапке карточки: живой наряд отменяется вместе с ней, материалы возвращаются.
- Поле «Этап» в карточке — только для чтения; этап меняется полосой этапов или на канбане.
- Автоматика в воронке — ровно один этап; выключить её нельзя, только включить на другом этапе. Такой этап не удаляется и не скрывается.
- Этап со сделками удаляется только с переносом сделок (не на завершающий этап); этап цеха с работами — не удаляется (по нему считается зарплата).
- Сделку с нарядом в цеху не удалить — сначала отмена наряда. Живой наряд не удаляется, а отменяется. Материал с движениями склада или позициями прайса не удаляется. Это проверяется в модели и в действиях, а не только в политике: администратор проходит любую политику.

**Прайс**
- Снять с продажи ≠ удалить: снятая позиция не предлагается новым дверям, но в старых заказах считается и списывается.
- Позицию, выбранную хоть в одной двери, удалить нельзя.
- Вариант по умолчанию в группе один.

**Деньги и склад**
- Платёж без чека не сохраняется; сумма платежей не больше суммы сделки — проверяется при каждом сохранении платежа на сервере. Если спецификацию урезали ниже внесённого, карточка предупреждает.
- Расход попадает в сводку и списывается со счёта только после подтверждения администратором; для всех категорий, кроме зарплаты и налогов, нужен чек. Подтверждённый расход не удаляется — только отклоняется с причиной.
- Автобонус со сделки начисляется один раз на сделку, ответственному менеджеру, от суммы на момент закрытия; ставку меняет только администратор. Сотрудник видит только свою зарплату и бонусы.
- Ведомость: удержания правятся только в черновике; утверждённая не пересчитывается (повышение оклада не меняет прошлый месяц); выплата не больше остатка и только по утверждённой; утверждённый бонус не удаляется.
- Платёж по долгу не больше остатка; долг с остатком нельзя отметить погашенным; долг с платежами не удаляется. Платит по долгам администратор.
- Остаток кассы и банка не хранится, а считается по журналу движений: платёж по сделке — приход, подтверждённый расход — списание, наличные в кассу, остальное в банк. Руками — только перевод между счетами и корректировка администратора с причиной.
- Списание при повторной передаче не задваивается; наряд по сделке создаётся один. Готовый наряд тоже считается «уже передано»: сделку, возвращённую назад и снова доведённую до передачи, второй раз на завод не отправят.
- Сдельная оплата — тому, кто взял этап в работу, иначе тому, кто закрыл (только цех); не тому, кто открыл следующий.
- Отменённый или закрытый наряд не берётся в работу, не закрывается и не отменяется повторно.

**Время**
- Время на этапе копится за все заходы (`deal_stage_visits`); норматив этапа сравнивается с суммой.
- Просрочка считается только у открытых сделок. Ежедневная проверка и страница «Просроченные» считают просрочку этапа одинаково — по сумме заходов. Продажам по сроку сдачи показываются сделки, а не их наряды (иначе один заказ считался бы дважды).

## 7. Экраны

**Продажи:** Воронка продаж (канбан, drag & drop + кнопки ← → для тач-экранов) · Сделки (список из блоков со сводкой: в работе, ждут завод, просрочено, ожидаем оплату) · Карточка сделки в духе amoCRM (полоса этапов сверху, вкладки Клиент / Двери / Оплата / Договор, сводка справа, история внизу) · Просроченные (три вкладки: срок сдачи, замер, застряли на этапе; самая большая просрочка сверху).

**Завод:** Воронка завода (канбан нарядов; на последнем этапе вместо «→» кнопка «Готово ✓», она же в карточке наряда; подтверждения — модалки в стиле панели) · Планшет цеха `/shop` (крупные карточки, выбор исполнителя, «Взять в работу» / «Готово», без сумм) · Зарплата цеха (сдельно по закрытым этапам за месяц; оклад — в карточке сотрудника).

**Склад:** остатки с минимальным порогом, приход, движения.

**Финансы** (группа меню для admin/manager): Обзор `/admin/finance` — ДДС (деньги на счетах и долги), сумма договоров, дебиторка, поступления, расходы по категориям, результат, склад по учётной цене, фильтр по месяцу · Счета `/admin/invoices` — по сделкам: выставлено, оплачено, остаток; вкладки «ожидают / просрочены / оплачены», приём оплаты и напоминание · Поступления `/admin/incomes` — все платежи по сделкам с итогами и модалкой «Добавить поступление» · Расходы `/admin/expenses` — категории, чек, статусы «на проверке / оплачено / отклонено», подтверждает администратор · Касса и банк `/admin/cash` — счета с остатками по журналу, переводы, корректировки · Задолженности `/admin/debts` — кому должны, платёж создаёт расход и списание, долг закрывается только по факту · Зарплата `/admin/salary` — ведомость за месяц: оклад (пропорционально дням приёма) + сдельно + утверждённые бонусы − удержания − авансы; черновик пересчитывается, утверждённая зафиксирована, выплата создаёт расход «Зарплата» и списание · Бонусы `/admin/bonuses` — начисляют продажи и администратор, утверждает администратор; автобонус менеджеру — процент от суммы сделки при её закрытии (по умолчанию 2 %, ставка в «Настройки → Финансы», у сотрудника может быть своя) · Моя зарплата `/admin/my-salary` — любой сотрудник видит только свои оклад, сдельно, бонусы, выплаты · Зарплата цеха (сдельно по этапам). Мои расходы, закуп как расход, отчёты — по шагам в `finance-plan.md`.

**Настройки (admin):** Этапы воронок (конструктор в духе Битрикс24: перетаскивание, переименование в строке, цвет, шестерёнка с нормативом/оплатой/обязательными полями, меню «⋯» с автоматикой) · Прайс конфигуратора (bento-сетка по группам опций) · Сотрудники (карточка с показателями, активностью, зарплатой) · Экран цеха (код планшета).

**Профиль** `/admin/profile`: каждый меняет только своё — имя, контакты, фото, пароль. Роль и оклад — у администратора.

**Клиент** `/track/{hash}`: статус заказа, позиции, сумма, QR.

**Ежедневно 08:30** (`gravit:daily-check`): уведомления руководству о материалах ниже минимума и нарядах на этапе дольше норматива (со ссылкой на «Просроченные»).

## 8. Дизайн

Light SaaS / glassmorphism, компактная плотность (поля 34 px, между полями 14 px, строка таблицы ~57 px). Три уровня поверхностей: карточка страницы (белая, тень) → блок внутри (плоский серый) → блок внутри блока (снова белый). Просрочка — красным везде: кромка карточки, пилюли «просрочено N дн.», таймер этапа сверх норматива. Все токены — в `resources/css/filament/admin/theme.css`, общие правила Filament — в `AppServiceProvider`. Адаптив проверен на 390 / 820 / 1680 px. Тёмная тема есть, но глазами проверена не везде.

## 10. История разработки (сентябрь 2026)

1. **Ядро** — две воронки, автоматизация продажи ⇄ завод, конфигуратор, склад, планшет цеха, страница клиента, роли.
2. **Карточка сделки** — переделана под amoCRM: полная карточка клиента, несколько дверей в сделке, полоса этапов, регламент обязательных полей, каталог (линейка/модель), документы, валидация, замерщик с уведомлениями.
3. **История сделки** по отделам, автонумерация позиций, адаптив, карточка сотрудника и профиль.
4. **Деньги** — платежи с обязательным чеком вместо одного поля «предоплата».
5. **Дизайн** — система поверхностей, компактная плотность, bento-прайс, список сделок из блоков.
6. **Конструктор воронок** в духе Битрикс24 с правилами целостности.
7. **Проверка корректности** сквозным сценарием и Larastan. Найдены и исправлены: сдельная оплата уходила не тому; повторная передача после отмены не создавала наряд; закрытая сделка оставалась открытой; сделка обгоняла завод; поле «Этап» обходило воронку; снятая с продажи позиция ломала старые заказы.
8. **Просрочка** — срок сдачи обязателен, красным везде, страница «Просроченные», просроченный замер.
9. **Время на этапе** — журнал заходов вместо «времени с последнего входа», восстановление из истории.
10. **Закрытие наряда с канбана и из карточки** — у «ОТК и Упаковка» нет соседа справа, стрелка «→» была отключена, и наряд можно было завершить только с планшета цеха. Добавлена кнопка «Готово ✓» на канбане завода и под полосой этапов наряда; подтверждения переведены с системного `confirm()` на модалки Filament, на планшете — своя модалка.

## 11. Что осознанно не сделано / на будущее

- **Закрытие сделки необратимо** из интерфейса — «переоткрыть» нужно отдельным действием, если понадобится.
- **Категория и модель двери не влияют на цену** — она считается от материалов. Если у Premium/Lux своя надбавка, её место в прайсе.
- **Чеки и документы лежат в публичном хранилище**: имена случайные, но по прямой ссылке файл откроется без входа. Для боевого запуска — закрыть доступ.
- **Переделка готового заказа** (второй наряд по сделке с готовым нарядом) не предусмотрена: готовый наряд считается «передано», повторной передачи не будет. Если переделки нужны — отдельное действие «Новый наряд на переделку» с явным списанием.
- **Статусы «Отгружено» и «Установлено»** есть в перечислении, но не ставятся: после завода сделка «Готово к отгрузке» до самого закрытия. Клиент на `/track` этих шагов не видит.
- **Склад может уходить в минус** (`gravit.allow_negative_stock = true`) — списание не останавливается при нехватке; включите запрет перед боем.
- **События** `DealHandedToProduction`, `DealStageChanged`, `ProductionCompleted` диспатчатся, слушателей нет — это точки для интеграций (WhatsApp, 1С).
- **Колонка `deals.payment_method`** не используется ни в одной форме — способ оплаты живёт в платежах; колонку можно убрать.
- **Иконка этапа** показывается на канбане, но в конструкторе воронок не редактируется: новые этапы без иконки.
- **Демо-чеки** в сидере — `.txt`, а форма принимает фото и PDF.
- **Финансовый контур** — шаги 1–8 и 13 сделаны, 9–12 в `finance-plan.md`.
- **Роли по матрице** (директор, бухгалтер, HR, производство, менеджер «только свои») и **настройки сайта** (права, справочники, реквизиты, тексты, коэффициенты) — не начаты; план в `roles-and-settings-plan.md`.
- **Перед боем:** MySQL/Postgres вместо SQLite, очередь и планировщик как службы, CI.
- Не сделаны: печатные формы (наряд с QR, счёт, договор), дебиторка как отдельный контур, ТВ-экран с рейтингами.
