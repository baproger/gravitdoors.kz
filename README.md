# Gravit ERP — производство металлических входных дверей

ERP для завода входных дверей: две связанные воронки (**Отдел продаж ⇄ Завод**), конфигуратор
двери с расчётом цены и себестоимости, склад с автоматическим списанием и возвратом материалов,
планшет цеха, сдельная зарплата и публичная страница заказа по QR-коду.

## Технологии

| Слой | Что использовано |
|---|---|
| Backend | Laravel 12, PHP 8.3+ |
| Админка | Filament v4 (на Livewire v3) |
| Экран цеха | Livewire v3, отдельный публичный маршрут |
| Стили | Tailwind CSS v4 + Vite |
| БД | SQLite из коробки, MySQL/PostgreSQL — сменой `DB_*` в `.env` |
| QR | `bacon/bacon-qr-code`, инлайн-SVG без файлов |

> **Про версии.** В ТЗ значились Laravel 11 + Filament v3. Взяты Laravel 12 + Filament v4:
> Laravel 11 официально поддерживает PHP до 8.4, а на машине PHP 8.5 — установка ломалась бы
> на `composer install`. API Filament v4 отличается неймспейсами (`Filament\Schemas\*` для
> layout-компонентов), вся логика ТЗ реализована без изменений.

## Архитектура воронок

Обе воронки живут в **одной** таблице `deals`, различаясь колонкой `pipeline_type`:
производственный наряд — это та же сделка с `pipeline_type = factory` и ссылкой
`parent_deal_id` на сделку продаж. Связка «продажи ⇄ завод» остаётся одним JOIN,
а не синхронизацией двух сущностей, которые рано или поздно разойдутся в данных.

Этапы обеих воронок настраиваются в админке (**Настройки → Этапы воронок**): название,
порядок перетаскиванием, цвет, норматив часов, сдельная расценка. Новый этап не требует
правки кода.

### Правила автоматизации

Живут в `app/Services/DoorProductionService.php` и **только** там — ни канбан, ни ресурсы
Filament, ни планшет цеха не двигают сделки напрямую, иначе перетаскивание карточки, кнопка
в карточке и кнопка на планшете разошлись бы в поведении.

**1. Продажи → Завод.** Сделка входит на этап с флагом `triggers_production`:
создаётся наряд на первом этапе цеха, со склада списываются материалы всех позиций,
статус сделки → «Передано в производство». Идемпотентно: второй наряд не появится.

**2. Завод → Продажи.** Завершается этап с флагом `completes_production` («ОТК и Упаковка»):
наряд закрывается, сделка продаж переходит в **«Готово к отгрузке»** и встаёт на следующий
этап воронки.

**3. Отмена наряда** возвращает материалы на склад по сальдо «списано − возвращено»
и возвращает сделку клиента в работу. Повторная отмена ничего не задваивает.

### Регламент воронки

Сделка идёт по этапам подряд — «сразу закрыть» её нельзя. Для входа на этап должны быть
заполнены обязательные поля; набор настраивается в админке (**Настройки → Этапы воронок →
Что обязательно заполнить**), из коробки:

| Этап | Что требуется |
|---|---|
| Замер и расчёт | телефон, адрес объекта, город, ответственный |
| Договор и предоплата | дата замера, хотя бы одна дверь, срок сдачи, реквизиты компании |
| Передано в производство | номер и дата договора, загруженный договор, предоплата |
| Сделка закрыта | оплачено полностью |

Назад сделку можно вернуть всегда: откат нужен именно тогда, когда данные оказались
неверными, и запирать его нечем.

### Замеры

Когда менеджер ставит дату **и время** замера, замерщики (роли «Замерщик» и «Мастер цеха»)
получают уведомление «Замер 22.09.2026 в 14:30» с адресом и телефоном клиента. Перенос даты
уведомляет повторно, правка других полей — нет. Утром в 08:30 (`gravit:daily-check`) замерщики
и ответственный менеджер получают список выездов на день; если день замера прошёл, а сделка
не дошла до договора, о просрочке узнают директор и ответственный менеджер, а сделка помечена
красным в карточке, на канбане и в «Просроченных».

С выезда замерщик возвращается и нажимает **«Замерял»** у нужного выезда в плитке «Замеры
сегодня» на инфопанели — там же висят и просроченные замеры, потому что страница
«Просроченные» ему не открывается. В модалке: высота, ширина и комментарий. Они ложатся в
сделку (`measurement_height`, `measurement_width`, `measurement_comment`, `measurement_done_at`,
`measurement_by_id`), показываются блоком «Результат замера» на вкладке «Клиент» и одной
записью «Замер» в истории, а ответственный менеджер получает уведомление со ссылкой на
карточку. Этап замерщик не двигает: право `DealPolicy::measure()` даёт только запись замера,
воронка остаётся за менеджером.

```
Отдел продаж:  Новая заявка → Замер → Договор → [Передано в производство] → Готово к отгрузке → Доставка → Закрыта
                                                          │ triggers_production        ▲
                                                          ▼                            │ completes_production
Завод:              Раскрой → Сварка → Покраска → Утепление/МДФ → Фурнитура → [ОТК и Упаковка]
```

## Схема данных

| Таблица | Назначение |
|---|---|
| `deals` | Сделки и наряды. Карточка клиента (тип, компания, БИН, два телефона, e-mail, город, источник), договор, условия оплаты (предоплата, способ, доставка, монтаж), `status_id` (int-enum `DealStatus`), `pipeline_type`, `current_stage_id`, `parent_deal_id`, `qr_code_hash` |
| `door_configurations` | **Позиции сделки**: одна строка — одна дверь. Габариты, сторона открывания, металл, панели МДФ, замок, утеплитель, покрытие, `additional_options` (json), `price_breakdown` (json) |
| `factory_stages` | Этапы **обеих** воронок (`pipeline_type`), порядок, `estimated_hours`, `operation_cost`, флаги автоматизации |
| `door_options` | Прайс конфигуратора: группа, цена, тип цены (фикс / за м² / за м.п.), привязка к складу и расход |
| `material_stocks` | Склад: остаток, минимальный порог, цена закупа |
| `stock_movements` | Приход, списание под наряд и возврат. Остаток `material_stocks.quantity` производен от этих строк |
| `production_logs` | Прохождение наряда по этапам: исполнитель, факт/норматив времени, зафиксированная сдельная выплата |
| `settings` | Настройки, меняемые владельцем: код планшета цеха |
| `users` | Сотрудники: роль, доступ, фото, оклад, дата приёма и день рождения |
| `deal_payments` | Платежи клиента: сумма, способ, дата, чек, кто принял |
| `deal_events` | История сделки: автор, отдел на момент действия, тип события, описание и разбор правок |

Одна сделка содержит **несколько дверей**: заказ на входную и тамбурную дверь — это одна
сделка с двумя позициями, а не две сделки, потерявшие связь в отчётах. Цена сделки —
сумма позиций, списание материалов — по всем позициям с агрегацией по номенклатуре
(одна строка расхода на материал, а не десяток мелких).

`status_id` — намеренно int-backed enum: колонка названа как в ТЗ, но в коде это
перечисление `DealStatus`. Шаг между значениями = 10, чтобы новые статусы вставлялись
без миграции данных.

## Калькулятор

`app/Services/DoorPriceCalculator.php`. Формула — «габариты × металл + панели МДФ + фурнитура»:

- **за м²** — цена умножается на площадь полотна (металл, МДФ, утеплитель, покрытие);
- **за м.п.** — на периметр коробки (уплотнитель);
- **фикс** — за изделие (замки, доводчик, глазок, броненакладка).

Ни одна цена не зашита в код — всё из `door_options`, правится в админке.
Себестоимость считается из другого источника: материалы (`consumption × price_per_unit`)
плюс сумма сдельных расценок этапов цеха. Расшифровка сохраняется в
`door_configurations.price_breakdown`, поэтому правка прайса задним числом не переписывает
историю уже посчитанных заказов.

Цена сделки — производная: её пересчитывает `DoorProductionService::syncPricing()` при
сохранении карточки, а не набирает менеджер руками.

## Прайс: снятые с продажи позиции

Позиция прайса записана в дверях заказов парой «группа + код». Поэтому:

| Действие | Правило |
|---|---|
| Выключить позицию | значит **снять с продажи**: новым дверям её не предлагают, но там, где уже выбрана, она продолжает считаться в цене и списываться со склада |
| Удалить позицию | только если она не выбрана ни в одной двери, включая заказы в корзине; иначе — снять с продажи |
| Код и группа | после создания не меняются; код создаётся из названия |
| Вариант по умолчанию | один в группе, только у позиции в продаже; у доп. опций его нет |

Раньше выключенная позиция молча выпадала из расчёта: при пересохранении старой сделки её
цена падала, материал не списывался, а форму сделки нельзя было сохранить — выпадающий список
не находил выбранное значение среди вариантов. Теперь выбранная снятая позиция остаётся в списке
с пометкой «снята с продажи».

## Время на этапе

Каждый заход сделки на этап пишется в `deal_stage_visits` (вошла / ушла). Таймер «⏱ N ч» на
канбане и в полосе этапов показывает **накопленное** время за все заходы: вернули сделку на
этап — прежние часы не пропадают, у таймера появляется «2-й заход» (на канбане — «↺»). У пройденных
этапов на полосе видно, сколько каждый занял. Норматив этапа тоже считается по накопленному времени.
Журнал ведёт наблюдатель сделки, поэтому все пути смены этапа (канбан, карточка, удаление этапа
воронки) попадают в него одинаково; для уже существующих сделок журнал восстановлен из истории смен этапов командой
`php artisan gravit:rebuild-stage-visits` (можно `--deal=ID`): история хранила каждую смену с точным
временем и названиями «откуда → куда», так что заходы собраны без домыслов.

## Просрочка

Срок сдачи — обязательное поле сделки. Просроченная дата горит красным везде: карточка на канбане
(красная кромка и «просрочено N дн.»), строка в списке, полоса этапов в карточке, наряд на планшете
цеха. Таймер этапа краснеет, когда сделка стоит на этапе дольше норматива (`estimated_hours`).

**Замер** просрочен, когда дата замера прошла, а сделка ещё не дошла до этапа, для которого
замер обязателен («Договор и предоплата» из коробки — настраивается в этапах воронки). После
этого этапа дата в прошлом — просто история, не просрочка. Метка «Замер просрочен N дн.» —
на канбане, в карточке (красная полоса и подсказка у поля), в списке и в «Просроченных».

`/admin/overdue-deals` — страница «Просроченные» с красным счётчиком в меню. Три вкладки:
«Срок сдачи прошёл», «Замер не проведён» и «Застряли на этапе» (дольше норматива); везде
самая большая просрочка сверху. Закрытые сделки просроченными не считаются. Цех видит
только свои наряды.

## Сделка ждёт завод

Пока у сделки продаж есть незавершённый наряд, по воронке её ведёт производство, а не менеджер.
Ручной переход **в любую сторону** запрещён — полосой этапов, стрелками и перетаскиванием на
канбане. Вперёд — потому что сделка обгоняла бы цех («Готово к отгрузке», а дверь ещё на
покраске). Назад — потому что сделка отрывалась бы от живого наряда.

- На канбане у такой карточки нет стрелок и перетаскивания, есть метка «Ждёт завод: <этап цеха>».
- В карточке сделки этапы заблокированы, под полосой — какой наряд и на каком он этапе.
- Дальше сделку переводит сам завод: закрытие «ОТК и Упаковка» ставит её на следующий этап
  после «Передано в производство» со статусом «Готово к отгрузке».
- Если заказ отменили, сначала отменяется наряд («Отменить наряд» в списке сделок) — после
  этого сделка снова двигается вручную. Кнопка «Отменить сделку» в карточке делает это одним
  действием: отменяет живой наряд, возвращает материалы и закрывает сделку статусом «Отменена».
- Готовый наряд считается «уже передано»: сделку, возвращённую назад и снова доведённую до
  «Передано в производство», второй раз на завод не отправят и склад не спишут.
- Статус сделки следует за этапом и в карточке только для чтения: до передачи — «В работе»,
  на этапах после завода — «Готово к отгрузке», завершающий этап — «Завершена».

Поле «Этап» в карточке сделки — **только для чтения**. Раньше оно писало этап напрямую, в обход
порядка этапов, обязательных полей и завода. Новая сделка начинается с первого этапа воронки.

## Этапы воронок

`/admin/factory-stages` — настройка воронок в духе Битрикс24, только для администратора.

- **Две вкладки** — «Отдел продаж» и «Завод». Сверху полоса «Как видят сотрудники» —
  воронка в том порядке, в каком она будет на канбане, с отметкой ⚡ у этапа автоматики.
- **Этапы строками** в двух группах: «Этапы в работе» и «Завершающие этапы». Порядок —
  перетаскиванием за «⋮⋮» или кнопками ↑ ↓ (на телефоне drag-события не приходят),
  название правится прямо в строке, цвет — по клику на кружок. Сохраняется сразу.
- **«+ Добавить»** в каждой группе. Новый рабочий этап встаёт перед завершающими.
- **Шестерёнка** — редкие настройки: описание, норматив, сдельная оплата (завод),
  обязательные поля (продажи).
- **Меню «⋯»** — назначить автоматику, сделать этап завершающим или рабочим, скрыть, удалить.

Порядок (`order`) и первый этап (`is_initial`) руками не задаются: после каждой правки
`PipelineStageService` расставляет 10, 20, 30… и отмечает первый видимый рабочий этап.
Код этапа генерируется из названия и при переименовании не меняется.

Правила, которые не дают сломать воронку:

| Действие | Правило |
|---|---|
| Удалить этап со сделками | только с выбором, куда перенести; в истории каждой сделки — запись. Раньше сделки молча оставались без этапа |
| Удалить этап цеха с работами | нельзя: по записям цеха считается зарплата; такой этап можно скрыть |
| Удалить или скрыть этап автоматики | нельзя, пока автоматика не назначена другому этапу |
| Автоматика | в воронке ровно один такой этап: включение на одном снимает флаг с остальных |
| Завершающий этап продаж | не может передавать сделку в производство |
| Последний рабочий этап | удалить, скрыть или сделать завершающим нельзя |
| Скрыть этап | только пустой; скрытый этап пропускается в последовательности этапов |
| Название | 2–60 символов, без повторов внутри воронки (без учёта регистра) |

## Карточка сотрудника и профиль

`/admin/users/{id}` — что человек сделал и сколько за это получит:

- **Показатели** кольцами: сделки, доведённые до отгрузки; закрытые наряды; этапы цеха за месяц.
- **Активность за неделю** — действия в системе и закрытые этапы цеха по дням.
- **Зарплата за месяц** = оклад + сдельная выработка из `production_logs`, с долей каждого.
- **Сделки, работа в цеху и последние действия** — списками со ссылками.
- Справа — фото, контакты, дата приёма со стажем, день рождения, оклад.

Свою карточку открывает любой сотрудник, чужую — только руководство. **Оклад видно
своему владельцу и администратору**: менеджеру список коллег нужен для назначения
ответственных, а не для сверки чужих зарплат.

`/admin/profile` — **свой профиль**: имя, телефон, e-mail, пароль и фото. Роль, оклад
и доступ в профиль не вынесены — их правит администратор в разделе «Сотрудники»,
иначе рабочий выписал бы себе оклад директора прямо из профиля. Аватар подтягивается
в шапку панели и в карточку; без фото показываются инициалы.

## Права доступа

Роли лежат в справочнике `roles` (`App\Models\Role`), а `users.role` хранит код роли. Плюс
**редактируемая матрица прав**: у каждой роли есть уровень доступа (нет / чтение / только свои /
полный) по каждому разделу и полномочию. Матрица правится в **Настройки → Роли и доступы**
(`/admin/access`) и действует сразу.

Семь базовых ролей помечены `is_system`: их можно переименовать, перекрасить и менять им права,
но не удалить — на их кодах держатся автоматизации и заведённые сотрудники. Свои роли директор
заводит там же кнопкой **«Создать роль»**: указывает название и роль-образец, с которой
копируются все 32 права. Кроме прав у роли две галочки поведения — **«Ездит на замеры»**
(уведомления о выездах и кнопка «Замерял») и **«Работает в цеху»** (сдельная оплата за закрытый
этап, виден в выборе исполнителя на планшете); раньше это решал `match` по перечню в коде.

Право **«Роли и доступы» не выдаётся никакой роли, кроме директора** — ни копированием, ни
руками в матрице: иначе роль смогла бы выписать себе все остальные права.

- `App\Enums\Permission` — что вообще можно разрешать (разделы меню и полномочия внутри экранов).
- `App\Enums\UserRole` — коды семи встроенных ролей; ими заполняется справочник при миграции.
- `App\Enums\AccessLevel` — четыре уровня, упорядоченные по силе.
- `App\Services\AccessControl` — единственный источник истины: кэш, отличия в `role_permissions`,
  рекомендованные значения из ТЗ как значения по умолчанию.
- `app/Policies/*` спрашивают уровень у реестра; прямых сравнений с ролью в коде нет.

Директор (`admin`) проходит любую политику через `Gate::before`, и его строку в матрице изменить
нельзя. Поэтому запреты вида «нельзя удалить подтверждённое» живут в моделях и в действиях.

| | admin | manager | surveyor | master | worker |
|---|:---:|:---:|:---:|:---:|:---:|
| Сделки продаж | ✓ | ✓ | — | — | — |
| Производственные наряды | ✓ | ✓ | — | ✓ | ✓ (просмотр) |
| Канбан завода, закрытие этапов | ✓ | — | — | ✓ | канбан только просмотр |
| Суммы и маржа | ✓ | ✓ | — | — | — |
| Прайс конфигуратора | ✓ | только чтение | — | — | — |
| Склад: остатки / приход | ✓ | ✓ | — | ✓ | — |
| Просроченные | ✓ | ✓ | — | ✓ | ✓ (без ссылок на карточки) |
| Уведомления о замерах | — | — | ✓ | ✓ | — |
| Этапы воронок, сотрудники | ✓ | — | — | — | — |
| Удаление сделок | ✓ (без наряда в цеху) | — | — | — | — |
| Отмена сделки | ✓ | ✓ | — | — | — |

Ограничение по воронке стоит на запросе (`DealResource::getEloquentQuery`), поэтому действует
и в списке, и в глобальном поиске, и по прямой ссылке. Перетаскивание карточки на канбане
перепроверяется политикой на сервере: разметка ничего не решает.
Отключённый сотрудник (`is_active = false`) не войдёт в панель. Переключатель «Доступ» в списке
сотрудников работает только у администратора: колонка-переключатель Filament минует политику,
поэтому запрет стоит на ней самой.

Администратор проходит любую политику, поэтому правила «нельзя удалить сделку с нарядом в цеху»,
«живой наряд не удаляется, а отменяется» и «материал с движениями не удаляется» живут в моделях
(`canBeDeleted()`) и проверяются действиями удаления и наблюдателем, а не только политикой.

## Инфопанель по ролям

Директор и бухгалтер видят инфопанель целиком: продажи, деньги, цех, склад, люди. У всех
остальных сверху блок **«Моя работа»** только со своими цифрами, а общих сводок нет:

- **Рабочий цеха** — сколько этапов закрыл за период и сколько сдельно заработал, какие
  наряды сейчас у него в работе (те, где нажал «Взял»). Загрузку цеха и выработку коллег
  не видит.
- **Начальник производства** — сводка по всему цеху (наряды, застрявшие, загрузка, выработка).
- **Замерщик** — замеры сегодня с временем, клиентом и адресом, просроченные выезды тем же
  списком, сколько на неделе, у каждого выезда кнопка «Замерял». Сумм сделок нет.
- **Менеджер** — свои сделки (как и раньше, через «только свои»), свои замеры сегодня, свой
  бонус за период и сколько ждёт утверждения, ссылка на «Мою зарплату». Таблицы по всем
  менеджерам нет.
- **Кадры** — блок по людям (ведомости, штат).

Логика — `DashboardStats::isFullView()` (полный вид: полное право на воронку продаж или
доступ к финансам), `seesFactoryOverview()` (сводка по цеху) и методы `my*()`.

## Где кнопка «Новая сделка»

Везде, где работает менеджер: в шапке панели на любой странице (справа от поиска),
в заголовке инфопанели, воронки продаж, списка сделок и страницы «Клиенты». Одна кнопка
(`App\Filament\Actions\NewDealAction`) — видна только тем, кто заводит сделки: директору
и менеджеру. У бухгалтера, кадров и цеха воронка продаж на чтение, им она не показывается.

## Клиенты и закрытые сделки

Закрытые сделки (завершённые и отменённые) не пропадают: в списке сделок у них своя вкладка
**«Закрытые»**, а на странице **«Клиенты»** (`/admin/clients`) все сделки продаж свёрнуты по
телефону клиента: имя или компания и БИН из последней сделки, город, сколько сделок и сколько
в работе, на какую сумму заказал, сколько должен, когда была последняя сделка. Поиск — по имени,
телефону, компании и БИН; менеджер с уровнем «только свои» видит только своих клиентов.

Из строки клиента: **«Сделки»** — список всех его сделок, **«Новая сделка»** — карточка
заполняется реквизитами из последней сделки (тип, имя, телефоны, e-mail, компания, БИН, город,
адрес объекта), менеджер только проверяет и переходит к дверям. Отдельной таблицы клиентов нет
намеренно: клиент вводится в сделке, и одно место ввода — меньше расхождений.

## Карточка сделки

Собрана как в amoCRM — чтобы менеджер вводил заказ в одном месте, не прыгая по разделам:

- **Полоса этапов сверху.** Клик двигает сделку через `DoorProductionService` — та же
  автоматика, что и на канбане. Вперёд открыт только соседний этап: воронку нельзя
  проскочить. Если для перехода не хватает данных, этап подсвечен оранжевым, а под полосой
  перечислено, чего именно и где. Если не хватает только оплаты, прямо в подсказке стоит
  кнопка «Принять оплату — остаток …». Права проверяются на сервере.
- **Кнопки в шапке — по отделам.** «Принять оплату» отдельно, остальное в группах
  **Отдел продаж** (передать в производство, пересчитать цену, отменить сделку),
  **Финансы** (заблокировать / снять блокировку отгрузки, напомнить об оплате),
  **Завод** (завершить этап, факт материалов, отменить наряд), **Клиент** (страница клиента,
  QR). Каждый видит только свою группу; пустые группы скрыты. Те же кнопки — в списке сделок
  и на странице «Счета»: одно определение (`App\Filament\Actions\DealActions`), одни права.
- **Вкладки слева** — «Клиент», «Двери», «Оплата», «Договор». Полные данные заказчика:
  физлицо или компания (реквизиты появляются только для компании), контактное лицо, два
  телефона, e-mail, город, адрес объекта, дата замера, откуда пришёл.
- **Двери** — список позиций, свёрнутый до строки «Позиция 1 · Premium Лион · 2050×950 мм».
  Внутри позиции три блока: «Изделие» (линейка Comfort/Premium/Lux и модель — Агора, Ажур,
  Лион, Монтана), «Размеры проёма» и свёрнутые «Характеристики» с материалами. Внизу —
  живой расчёт позиции. Номер позиции проставляется сам и перенумеровывается после удаления.
- **Договор** — номер, дата и загрузка документов: подписанный договор, счёт, акт
  (PDF, фото или Word, до 10 МБ каждый).
- **История сделки** под карточкой — кто, из какого отдела и что сделал: создание, правки
  полей со значениями «было → стало», смена этапов, передача в цех, закрытие этапов цеха
  с исполнителем, списание и возврат материалов, оплаты и документы. Фильтруется по отделу
  (Продажи · Замеры · Завод · Склад · Система) и по типу события. Отдел записывается
  в момент действия: если сотрудник сменит должность, история не перепишется.
- **Оплата** — сверху сумма сделки, оплачено и остаток, рядом кнопка **«Принять оплату»**:
  в окне уже подставлен остаток (при первом платеже — вся сумма договора), поправить можно,
  если клиент платит частями; платёж сохраняется сразу, без «Сохранить» внизу карточки.
  Ниже — список платежей клиента. У каждого платежа сумма, способ, дата, комментарий
  и **обязательный чек** (фото или PDF до 10 МБ): «клиент сказал, что перевёл» потом сверить
  нечем. Предоплата сделки считается сама как сумма платежей, сумма платежей не может
  превысить сумму сделки. Каждый платёж, его правка и удаление пишутся в историю с автором.
- **Сводка справа** видна с любой вкладки: двери по спецификации, доставка, монтаж,
  сумма сделки, предоплата, остаток к оплате. Себестоимости и маржи в карточке нет —
  они нужны в отчётах, а не при работе с клиентом.
- **Управление справа** — ответственный, статус, срок, этап.

Доставка и монтаж задаются в карточке и прибавляются к сумме сделки поверх спецификации
дверей; себестоимость при этом считается только по производству.

## Интерфейс

- **Список сделок** (`/admin/deals`) — сверху полоса показателей: «В работе» с суммой, «Ждут
  завод», «Просрочено» (краснеет, если есть что догонять) и «Ожидаем оплату» — остаток по
  открытым сделкам. Под ней вкладки «Отдел продаж / Завод / Все» и сами сделки — не таблица
  из десяти колонок, а строки из блоков: название с номером, клиентом и городом в одну строку;
  телефон со звонком по клику; этап и под ним что происходит сейчас («ждёт завод: Покраска»,
  «на этапе 2 дн.», итоговый статус у закрытых); сумма и остаток; срок («просрочено на 3 дн.»,
  «через 5 дн.») и ответственный. У просроченной открытой сделки красная кромка слева. На
  телефоне блоки встают друг под другом, без горизонтальной прокрутки. Поиск по названию,
  номеру, клиенту, компании, телефону и БИН; фильтры по воронке, статусу, этапу, менеджеру
  и источнику. Маржи в списке нет — себестоимость при работе с клиентом не показывается.
  Цех видит только наряды и без денег.
- **Канбан** (`/admin/kanban/sales`, `/admin/kanban/factory`) — перетаскивание карточек
  нативным HTML5 drag & drop на Alpine, без внешних библиотек. На тач-экранах такие события
  не приходят вовсе, поэтому у каждой карточки есть кнопки «← →» на соседние этапы: на
  телефоне это единственный рабочий способ двигать сделку, а на десктопе просто быстрее
  мышки. На последнем этапе цеха («ОТК и Упаковка») стрелке некуда вести, поэтому вместо
  «→» у наряда зелёная кнопка «Готово ✓»: закрывает этап, начисляет сдельную оплату и
  переводит сделку продаж в «Готово к отгрузке» — та же логика, что у планшета цеха. Та же
  кнопка есть под полосой этапов в карточке наряда. Колонка грузит 20 карточек и догружает
  остальные по кнопке — иначе на сотнях заказов страница переставала бы открываться;
  счётчик в шапке показывает полное количество.
- **Планшет цеха** (`/shop`) — публичный экран без логина: вход по коду, выбор исполнителя,
  крупные карточки, кнопки «Взял» и «Готово ✓», автообновление раз в 15 секунд.
  Ни сумм, ни данных клиента. Код выдаётся и перевыпускается в **Настройки → Экран цеха**.
- **Инфопанель** (`/admin`) — свой экран вместо набора виджетов: переключатель периода
  (сегодня / неделя / месяц / прошлый месяц / квартал / год / всё время / свой отрезок) живёт
  в адресной строке, поэтому ссылкой на отчёт можно поделиться. Плитки: продажи, деньги,
  производство, склад, люди; ниже — столбики «приход и расход по месяцам», полосы воронки
  продаж и загрузки цеха, расходы по статьям, менеджеры, источники заявок, выработка цеха,
  что пора закупать. Числа считает `App\Services\DashboardStats` по записям, видимым
  пользователю, а показывать ли блок — решает реестр прав.
- **Роли и доступы** (`/admin/access`, только директор) — матрица «право × роль»: строки
  сгруппированы по разделам, в ячейке уровень доступа, изменение действует сразу. Колонка
  директора закреплена, отличия от рекомендованных значений подсвечены, есть сброс прав роли.
  В базе хранятся только отличия, поэтому свежая установка работает без настройки. В шапке —
  «Создать роль» (копией с существующей), «Настроить роль» (название, цвет, описание, галочки
  поведения, показывать ли её в карточке сотрудника) и «Удалить роль» (только придуманную и
  только без сотрудников).
- **Карточка сделки только для чтения** (`/admin/deals/{id}`) — для тех, у кого уровень «чтение»:
  бухгалтер сверяет суммы и платежи, не имея права править сделку. Ссылки на карточку по всей
  системе идут через `DealResource::cardUrl()` и сами ведут либо на правку, либо на просмотр.
- **Блокировка отгрузки** — действие финансов в списке сделок: с обязательной причиной сделка
  перестаёт двигаться дальше этапа передачи в цех (`ProductionException::shipmentBlocked`),
  причина видна на канбане и под полосой этапов. Снимается тем же действием.
- **Факт материалов** — действие цеха на наряде: списать сверх плана или вернуть излишек.
  Движение склада привязано к наряду и автору, запись уходит в историю сделки.
- **Финансы — обзор** (`/admin/finance`, группа меню «Финансы», только admin/manager) — сумма
  договоров без отменённых, дебиторка по открытым сделкам, поступления с разбивкой касса/банк,
  расходы (сдельная оплата, оклады, закуп материалов), результат, склад по учётной цене; фильтр
  «месяц / за всё время». Цифры считает `App\Services\FinanceSummary`. Остальные разделы
  финансов (счета, поступления, расходы, касса, задолженности, ведомость, бонусы) — по шагам
  в `finance-plan.md`.
- **Счета** (`/admin/invoices`) — витрина по сделкам продаж: выставлено, оплачено, остаток, срок и
  дни просрочки; вкладки «Ожидают оплату / Просрочены / Оплачены / Все» с итогами; «Принять оплату»
  (та же проверка «не больше остатка») и «Напомнить» (запись в историю сделки). Бейдж в меню —
  просроченные.
- **Поступления** (`/admin/incomes`) — все платежи по сделкам одним списком: итоги (всего, касса,
  банк), фильтр по месяцу, способу и менеджеру, чек, «Добавить поступление» с выбором открытой сделки.
- **Задолженности** (`/admin/debts`) — кому должны: контрагент, категория, сумма, выплачено, остаток,
  срок; вкладки «Открытые / Просроченные / Погашенные». «Оплатить» (администратор) создаёт
  подтверждённый расход и списание со счёта; долг закрывается сам при нулевом остатке, руками с
  остатком не закрывается, с платежами не удаляется.
- **Расходы** (`/admin/expenses`) — категории (аренда, налоги, зарплата, материалы, транспорт, реклама,
  сервисы, коммунальные, прочее), сумма, дата, способ, счёт, контрагент, чек, привязка к сделке.
  Вкладки «На проверке / Оплачено / Все» с суммами. Менеджер вносит и правит свои неподтверждённые,
  администратор подтверждает (чек обязателен, кроме зарплаты и налогов) или отклоняет с причиной;
  подтверждённый расход не удаляется. В сводку и в кассу идут только подтверждённые.
- **Касса и банк** (`/admin/cash`) — счета (касса, банк) с остатком по журналу: начальный остаток +
  приход − расход. Движения создаёт `App\Services\CashLedger` из платежей по сделкам (наличные в
  кассу, карта/Kaspi/перевод в банк) и подтверждённых расходов; правка или удаление источника
  меняет движение. Руками — перевод между счетами и корректировка (администратор, с причиной).
  Старые платежи разносятся командой `gravit:finance-backfill` (идемпотентна).
- **Зарплата** (`/admin/salary`) — ведомость за месяц по всем активным сотрудникам: оклад
  (пропорционально дням, если принят внутри месяца), сдельно по закрытым этапам, утверждённые
  бонусы, удержания и авансы, к выплате, выплачено. «Сформировать» пересчитывает черновики;
  «Утвердить» фиксирует цифры; «Выплатить» (частями) создаёт расход «Зарплата» и списание со счёта.
  Логика — `App\Services\PayrollService`.
- **Бонусы** (`/admin/bonuses`) — сотрудник, месяц, сумма, за что, при желании сделка. Предлагают
  менеджер и администратор, утверждает администратор; утверждённый бонус попадает в ведомость и
  в карточку сотрудника, не удаляется — только снимается с утверждения.
- **Автобонус менеджеру** — при переводе сделки на завершающий этап ответственному менеджеру
  начисляется процент от суммы сделки (`App\Services\BonusAccrual`): один бонус на сделку, в месяц
  закрытия, со ссылкой на сделку и записью в её истории; менеджер получает уведомление. Ставка —
  **Настройки → Финансы** (`/admin/finance-settings`, только администратор): процент и режим
  «утверждать автоматически / администратором». В карточке сотрудника можно задать личную ставку.
- **Моя зарплата** (`/admin/my-salary`) — для любого сотрудника, включая цех: своя ведомость
  (или предварительный расчёт, пока её нет), выплаты, бонусы со статусами, закрытые этапы.
  Чужие цифры недоступны: все запросы привязаны к текущему пользователю.
- **Зарплата цеха** (`/admin/payroll`, группа «Финансы») — сдельно по закрытым этапам за месяц, факт против
  норматива, сотрудники без выработки.
- **Прайс конфигуратора** (`/admin/door-options`) — bento-сетка: сверху сводка (в продаже,
  групп заполнено, со склада, в заказах), под ней поиск и фильтры «Все / Со склада / В заказах /
  Сняты с продажи», дальше карточка на каждую группу опций с прозрачным градиентом своего
  цвета. В строке позиции: название, код, списание со склада, в скольких дверях выбрана,
  цена с единицей, ★ вариант по умолчанию, переключатель «в продаже», правка и меню «⋯»
  (выше, ниже, удалить). Менеджер видит прайс без кнопок правки.
- **Движения склада** (`/admin/stock-movements`) — журнал прихода, списания и возвратов,
  только чтение: остаток производен от этих строк.
- **Стиль** — Light SaaS / glassmorphism: `resources/css/filament/admin/theme.css`.
  Блоки формы, плитки и карточки канбана залиты мягким вертикальным градиентом —
  одинаково белые секции встык сливались в одно полотно.
- **Система поверхностей** вместо градиента на каждом слое. Три уровня, каждый отличается
  от соседнего одним признаком: карточка страницы — белая с рамкой и мягкой тенью на сером
  фоне; блок внутри карточки — плоский светло-серый без тени; блок внутри блока — снова
  белый. Один радиус на уровень, один отступ между крупными блоками. Раньше секция внутри
  вкладки внутри карточки несла три фона, три тени и радиусы 8/12/16 px вперемешку.
- **Компактная плотность** задана токенами (`--gd-*` в `theme.css`), а не разбросана по
  экранам: между полями 14 px вместо 24, заголовок страницы 24 px вместо 30, поля и кнопки
  34 px, верхняя панель 56 px, строка таблицы 57 px вместо 93. Модалки — 14–18 px отступа
  вместо 24 со всех сторон. Шаг меняется в одном месте. Экран цеха сознательно не уплотнён:
  там работают пальцами, и крупные кнопки нужнее.
- **Основной цвет — палитра `Color::Blue`**, а не `Color::hex`: из светлого hex Filament
  строил палитру, у которой тёмный тон не проходил проверку контраста, и кнопки рисовались
  бледными с тёмной подписью, как отключённые.
- **«Сохранить / Отмена» закреплены внизу экрана** плавающей панелью: у карточки сделки правая
  колонка выше формы, и кнопки оказывались далеко под вкладками.
- **Единые правила оформления** заданы один раз в `AppServiceProvider`, а не в каждом
  ресурсе: ширина модалок, компактные секции, полосатые таблицы. Иначе одинаковые по
  смыслу окна получались разной ширины и плотности, и панель выглядела собранной из кусков.
- **Формы ресурсов идут в одну колонку.** По умолчанию Filament ставит секции рядом,
  и в модалке поля сжимались до нечитаемых обрубков — цена «12 000» показывалась как «1»,
  дата рождения как «05.11.198».
  Панель по умолчанию в светлой теме, переключатель у пользователя остаётся.
- **Публичная страница** `/track/{qr_hash}` — статус, все позиции заказа, таймлайн этапов,
  прогресс цеха и QR-код. Адаптивная, светлая и тёмная тема. Себестоимость, маржа
  и внутренние заметки на неё не попадают.

## Адаптивность

Проверено на телефоне (390 px), планшете (820 px) и десктопе:

- **Канбан и планшет цеха** — колонка почти во всю ширину экрана телефона с прокруткой
  по одной (scroll-snap); на планшете видно две-три колонки. Кнопки перемещения увеличены
  до 40 px, чтобы попадать пальцем.
- **Полоса этапов** в карточке сделки до 1024 px прокручивается горизонтально со снапом:
  переносом в четыре ряда она съедала половину экрана.
- **Карточка сделки** — сетки Filament сворачиваются в одну колонку сами; вкладки и полоса
  этапов прокручиваются, сводка уходит под форму.
- **Таблицы** — номер сделки перенесён в описание (отдельной колонкой он съедал треть
  ширины телефона), второстепенные колонки появляются с `md`, `lg` и `xl`.
- **Страница клиента** `/track/{hash}` — одноколоночная вёрстка, крупный QR, светлая
  и тёмная тема.

## Безопасность

- **Файлы закрыты.** Чеки, договоры, документы и аватары лежат в `storage/app/private`,
  а не в `public/storage`. Наружу файл отдаётся только по подписанной ссылке на 30 минут
  (`App\Support\Uploads\PrivateFiles`), которую получает тот, кто вошёл и открыл карточку.
  Подделать подпись нельзя, прямой адрес не работает. Диск задан один раз для всех полей
  загрузки в `AppServiceProvider`.
- **Двухфакторный вход** через приложение-аутентификатор (Google Authenticator, Яндекс.Ключ,
  1Password): профиль → «Двухфакторная аутентификация». Коды восстановления — на случай потери
  телефона. Секрет и коды хранятся зашифрованными. Директору и бухгалтеру стоит включить в первый день.
- **Вход**: 5 попыток в минуту, дальше пауза. Код планшета — 10 попыток в минуту с адреса.
  Страница клиента — 30 запросов в минуту с адреса.
- **Заголовки** на каждом ответе (`App\Http\Middleware\SecurityHeaders`): нельзя встроить панель
  в чужой iframe, браузер не угадывает тип файла, адреса карточек не утекают в Referer,
  HSTS на год при HTTPS.
- **HTTPS принудительно** при `APP_URL=https://…`, кука сессии только по HTTPS (`SESSION_SECURE_COOKIE`),
  доверенные прокси — `TRUSTED_PROXIES`.
- **Права на сервере**: политики, `Deal::visibleTo()`, `Gate::before` для директора; сумма, статус
  и этап сделки не принимаются из формы. Загрузки ограничены типами (фото, PDF, Word) и 10 МБ.
- **Зависимости**: `composer audit` и `npm audit` без известных уязвимостей на 19 сентября 2026.

## Загрузки: сжатие фото и документов

Всё, что загружают в систему — чеки платежей и расходов, договоры и документы сделки,
документы по долгам, аватары — сжимается при сохранении (`App\Support\Uploads\UploadCompressor`).
Подключено одной настройкой ко всем полям загрузки Filament (`AppServiceProvider`), поэтому
новое поле сжимается само.

- **Фото (JPEG, PNG, WebP)**: разворот по EXIF, длинная сторона до 1600 px, JPEG 82 %.
  Фото чека с телефона 4–8 МБ → 200–400 КБ, всё читается. Картинка с прозрачностью — WebP.
  Уменьшение начинается ещё в браузере (FilePond), поэтому с телефона грузится быстро.
- **PDF**: пересборка через Ghostscript (`gs`), если он есть на сервере; результат берётся,
  только если стал заметно меньше. На виртуальном хостинге `gs` обычно нет — PDF остаются как есть.
- **Word и прочее**: без изменений.
- Снимок, который не помещается в память PHP, сохраняется как есть — лучше оригинал, чем
  потерянный чек.

Настройки в `.env`: `GRAVIT_UPLOAD_MAX_SIDE` (1600), `GRAVIT_UPLOAD_QUALITY` (82),
`GRAVIT_UPLOAD_PDF` (true), `GRAVIT_GHOSTSCRIPT` (путь к `gs`).

## Настройки

  возвращает склад до тысячных и разрешает повторную передачу; двойная передача даёт один наряд;
- список сделок: сводка считает сделки в работе, ждущие завод, просроченные и остаток к оплате
  без отменённых; в строке видно «ждёт завод» и «просрочено на N дн.» только у открытых; поиск по
  телефону; маржи в списке нет; цех не видит денежную сводку;
- прайс: код и группа не меняются при правке, по умолчанию один вариант в группе, позицию из
  заказа не удалить, снятая с продажи позиция не предлагается новым дверям, но старый заказ
  сохраняется с прежней ценой и списывает её материал; страница — карточки групп, поиск,
  создание в группе, правка, звёздочка, менеджер без правок, цех без доступа;
- сделка ждёт завод: пока наряд в цеху, сделку нельзя сдвинуть ни вперёд, ни назад — ни в
  сервисе, ни стрелкой канбана; завод по-прежнему переводит её сам; после отмены наряда сделка
  снова свободна; поле «Этап» в карточке не обходит воронку, новая сделка стартует с первого этапа;
- этапы воронок: новый этап встаёт перед завершающими, порядок перенумеровывается без
  дыр, удаление со сделками требует переноса и пишет историю, этап цеха с работами и этап
  автоматики не удаляются, автоматика уникальна, последний рабочий этап не убирается,
  скрытый этап пропускается воронкой; страница — добавление, перетаскивание, откат
  неудачного переименования, удаление с переносом, настройки, доступ только администратору;
- платежи: предоплата равна сумме платежей, удаление платежа её уменьшает, без чека платёж
  не сохраняется, сумма платежей не больше суммы сделки, чек загружается из карточки;
- экран цеха: исполнитель выбирается из списка строкой из `<select>`, чужого подставить нельзя;
- открытие всех экранов панели и наличие спецификации в карточке сделки.

## Развёртывание на маленьком сервере

Проект рассчитан на 1 ГБ памяти, 2 vCPU и 15 ГБ диска. Замер: страница панели
занимает 65–75 МБ на пике и 4–50 запросов к базе; три процесса PHP-FPM
покрывают отдел продаж, цех и бухгалтерию одновременно.

- База в бою — MySQL от hoster.kz: в коде нет SQL, привязанного к движку, и весь набор тестов
  проходит на MySQL так же, как на SQLite (`composer test:mysql` поднимает базу `gravit_test`
  на локальном MySQL и гонит тесты). Бэкап на MySQL идёт через `mysqldump` в одной транзакции.
- `docs/server.md` — бюджет памяти, MySQL hoster.kz, настройки PHP-FPM, opcache, nginx, cron, диск.
- `.env.production.example` — боевой `.env`: кэш и сессии в файлах, очередь
  синхронная, логи 7 дней уровня `warning`, SQLite в WAL.
- Код — в приватном репозитории `github.com/baproger/gravitdoors.kz` (`main`).
- **Бой — виртуальный хостинг hoster.kz с Plesk**, PHP 8.4: Git-развёртывание из панели,
  `bash deploy/plesk-deploy.sh` как действие при развёртывании, планировщик раз в минуту.
  Пошагово — `docs/plesk.md`. Без SSH и Composer — архив `deploy/build-release.sh` с `vendor`.
- Зависимости закреплены под PHP 8.3+ (`composer.json` → `config.platform.php`): тесты
  проходят на 8.4 и 8.5.
- `deploy/` для VPS (на случай переезда): `bootstrap.sh`, `server-setup.sh` (пакеты, swap,
  PHP-FPM, nginx, cron), `push.sh` (rsync без GitHub), конфиги nginx, PHP-FPM, opcache и cron.
- `php artisan gravit:install` — первый запуск на бою: миграции, справочники без демо-данных
  (этапы, склад, касса, прайс) и директор. Повторный запуск справочники не трогает.
- `deploy.sh` — обновление одной командой: проверка диска, бэкап, миграции, кэши,
  reload PHP-FPM, состояние сервера в конце.
- `php artisan gravit:backup` — снимок базы через `VACUUM INTO` / `mysqldump` и архив файлов;
  14 копий базы и 3 архива файлов (`--keep`, `--keep-files`); архив файлов пропускается,
  если после него на диске осталось бы меньше порога. Запускается планировщиком в 03:00.
- `php artisan gravit:server-check` — диск, память, свежесть бэкапа; в 08:00 предупреждает директора.
- Уведомления панели опрашиваются раз в 2 минуты, а не каждые 30 секунд: десять открытых
  вкладок иначе давали 20 запросов в минуту на трёх PHP-процессах.
- `public/build` хранится в git: Node на сервере не нужен.

Внутри кода под это же: права, настройки и ворота замера запоминаются на
запрос (`AccessControl`, `Setting`, `FactoryStage::measurementGate`), сводки
инфопанели и финансов считают каждую сумму один раз (`RemembersResults`),
график по месяцам — два сгруппированных запроса вместо 24.

## Что осознанно не сделано

Финансовый контур (счета, платежи, дебиторка), оклад и удержания поверх сдельной части,
печатные формы (наряд с QR, счёт, акт), ТВ-экран с рейтингами, аналитика,
многоцеховая структура, интеграции (WhatsApp, 1С).

Перед боевым запуском: перевести БД на MySQL/PostgreSQL, очередь с `sync` на `database`
или Redis, добавить PHPStan/Larastan и CI.
