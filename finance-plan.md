# Финансы — план реализации (для следующей модели)

> Цель: отдельный раздел **Финансы** в Gravit ERP по образцу финансового модуля qazaqtas.kz:
> Обзор · Счета · Поступления · Расходы · Касса · Задолженности · Мои расходы · Зарплата · Бонусы.
> Шаг 1 (Обзор) уже сделан. Дальше — по шагам ниже, строго по порядку: каждый шаг опирается на предыдущий.
>
> Перед началом прочитай `project.md` (суть и правила) и `README.md` (экраны, тесты). Стиль кода, комментариев
> и тестов — как в проекте: русские комментарии «почему», PHP-enum'ы, правила на сервере, Filament v4 (Schemas),
> плитки `gravit-bento / gravit-tile`, деньги через `App\Support\Money::format`.

---

## 0. Общие правила для всех шагов

- **Доступ.** Весь раздел «Финансы» — только роли с `UserRole::seesMoney()` (admin, manager). Записи создают admin и manager; удаляют и подтверждают — только admin. Цех (master, worker) и замерщик раздел не видят. На каждой странице `canAccess()`, на каждом ресурсе — политика в `app/Policies`, на действиях таблиц — `->authorize()`. Помни: **администратор проходит любую политику через `Gate::before`**, поэтому правила вида «нельзя удалить X с историей» ставятся в модель (`canBeDeleted()`) и в действие, как сделано для `Deal` и `MaterialStock`.
- **Деньги.** Суммы — `decimal(14,2)`, формат — `Money::format`. Валюта из `config/gravit.php`.
- **Период.** Каждая страница финансов имеет фильтр «месяц / за всё время» (образец — `FinanceOverview::$month`, `FinanceSummary::month()`). Единая логика периода — в `FinanceSummary`, не дублировать.
- **История.** Каждое денежное действие оставляет запись: для сделок — `DealEvent::record(...)`, для новых сущностей — колонка `user_id` (кто внёс) и `approved_by` / `approved_at` (кто подтвердил).
- **Файлы.** Чеки и документы — на диск `public` в подпапку (`expenses/`, `debts/`), как `deal_payments.receipt_path`. Это временно: см. project.md §11 про закрытие публичного хранилища.
- **Навигация.** Группа `NavigationGroup::make('Финансы')` уже есть. Порядок `navigationSort`: Обзор 10, Счета 20, Поступления 30, Расходы 40, Касса 50, Задолженности 60, Зарплата цеха 70, Зарплата (ведомость) 75, Бонусы 80, Мои расходы 90.
- **Тесты.** На каждый шаг — файл `tests/Feature/Finance<Шаг>Test.php`: доступ по ролям, правила сервера, сходимость сумм с Обзором. Плюс строка в `AdminPanelSmokeTest::panelPages()`. После шага: `php artisan test`, `vendor/bin/pint`, `vendor/bin/phpstan analyse` (базовый долг ~50 ошибок про `$this->record` — не увеличивать).
- **Документация.** После каждого шага — абзац в `README.md` (раздел «Экраны») и строка в `project.md` §7 и §10.
- **Не делать.** Не трогать логику воронок (`DoorProductionService`), не менять `deal_payments` (поступления по сделкам уже есть и покрыты тестами), не добавлять внешние пакеты.

## Шаг 2. Расходы (`/admin/expenses`) — СДЕЛАНО

Файлы: миграция `create_expenses_table`, `app/Enums/ExpenseCategory.php`, `ExpenseStatus.php`, `app/Models/Expense.php`, `app/Observers/ExpenseObserver.php`, `app/Policies/ExpensePolicy.php`, `app/Filament/Resources/Expenses/*`, `tests/Feature/FinanceExpensesTest.php`. Реализовано как описано ниже; чек проверяется при подтверждении, а не при вводе.

**Таблица `expenses`**: `id`, `category` (enum `ExpenseCategory`: rent, tax, salary, materials, transport, marketing, software, utilities, other), `amount`, `spent_at` (date), `method` (enum `PaymentMethod`, уже есть: cash/card/kaspi/transfer), `account_id` (nullable, FK на `cash_accounts` — появится в шаге 3, миграцию делать сразу nullable), `counterparty` (string, nullable), `comment` (text, nullable), `receipt_path` (nullable), `user_id` (кто внёс), `status` (enum `ExpenseStatus`: pending, approved, rejected), `approved_by`, `approved_at`, `deal_id` (nullable — расход по конкретной сделке, например доставка), timestamps, softDeletes. Индексы: `spent_at`, `category`, `status`.

**Ресурс** `app/Filament/Resources/Expenses/` (ExpenseResource + Pages/ManageExpenses + Schemas/ExpenseForm + Tables/ExpensesTable), как у `MaterialStocks`. Список: вкладки «На проверке» / «Оплачено» / «Все», сумма по вкладке в бейдже, фильтры по категории, месяцу, способу. Действия строки: «Подтвердить» (admin; ставит approved, approved_by/at), «Отклонить» (admin, причина), «Чек». Массовое: подтвердить выбранные.

**Правила сервера**: сумма > 0; дата не в будущем; чек обязателен для категорий кроме salary/tax (валидатор в форме + проверка в `ExpenseObserver::saving`); подтверждённый расход не редактируется (кроме admin) и не удаляется — `canBeDeleted()` = `status !== approved`.

**Связь с Обзором**: `FinanceSummary::expenseLines()` — добавить «Прочие расходы» = сумма `approved` расходов по категориям за период (каждая категория отдельной строкой, как на скриншоте: Аренда, Налог, Прочее…). `salaries()` и `purchases()` оставить как есть до шага 7/9.

**Тесты**: менеджер создаёт, не подтверждает; admin подтверждает; чек обязателен; подтверждённый не удаляется; суммы по периоду попадают в Обзор; master не видит страницу.

**Готово, когда**: на Обзоре в блоке «Расходы» строки по категориям сходятся с вкладкой «Оплачено».

## Шаг 3. Касса и банк (`/admin/cash`) — СДЕЛАНО

Файлы: миграция `create_cash_accounts_and_movements` (+ `deal_payments.account_id`), `app/Enums/CashAccountType.php`, `app/Models/CashAccount.php`, `CashMovement.php`, `app/Services/CashLedger.php` (единственная точка записи движений), `app/Filament/Pages/CashDesk.php`, `database/seeders/CashAccountSeeder.php`, `app/Console/Commands/FinanceBackfill.php`, `tests/Feature/FinanceCashTest.php`. Обзор показывает остатки счетов. Не сделано из описания: выбор счёта в форме платежа сделки (берётся по способу оплаты; поле `account_id` в таблице есть) — добавить в шаге 4 вместе с модалкой «Добавить поступление».

**Таблица `cash_accounts`**: `id`, `name`, `type` (enum `CashAccountType`: cash, bank), `opening_balance`, `opening_at` (date), `is_active`, `note`, timestamps. Сидер: «Касса (наличные)», «Банк (расчётный счёт)».

**Таблица `cash_movements`** — единый журнал денег: `id`, `account_id`, `direction` (in/out), `amount`, `happened_at`, `source_type` + `source_id` (morph: DealPayment, Expense, Debt-платёж, ручная корректировка, перевод между счетами), `comment`, `user_id`, timestamps. Индексы: `account_id, happened_at`.

**Автоматика** (наблюдатели, транзакции):
- создан/изменён/удалён `DealPayment` → движение `in` на счёт по способу оплаты (`cash` → счёт типа cash, иначе → bank; выбор счёта — поле `account_id` в форме платежа, по умолчанию первый активный нужного типа);
- расход `approved` → движение `out` на его счёт; отклонён/удалён → движение снимается;
- «Перевод между счетами» — действие на странице: два движения (out/in) с одним `transfer_id`;
- «Корректировка» (admin) — ручное движение с обязательной причиной (инвентаризация кассы).

**Страница «Касса»**: плитки по каждому счёту: остаток = opening_balance + Σin − Σout; ниже — журнал движений с фильтром по счёту и месяцу. Остаток пересчитывается запросом, не хранится.

**Обратная совместимость**: платежи, внесённые до шага 3, разнести командой `gravit:finance-backfill` (по `method` → счёт). Команда идемпотентна (проверяет наличие движения по source).

**Тесты**: платёж создаёт движение; удаление платежа удаляет движение; подтверждение расхода списывает; перевод сохраняет сумму по счетам; backfill не задваивает.

**Обзор**: плитки «Остаток в кассе» и «Остаток в банке» — из остатков счетов (заменить текущие «касса/банк» из поступлений).

## Порядок работы для каждого шага

1. Миграция + модель (fillable, casts, связи, `canBeDeleted()`) + enum'ы + фабрика.
2. Политика + `canAccess`.
